# Part A — Streaming breaks FL's core selection assumption

### The assumption we break
- Every selection system (Oort, REFL, FedDance) assumes a **fixed, whole dataset** per client
- Scores each client by a **stale, last-trained utility**
- Production clients **stream** data → that assumption is false; **no system models it**

### Streaming hurts twice
- **Direct:** less data early → slower (expected, uninteresting)
- **Misprioritization (the interesting part):** true utility is a **moving target**
  - new data → utility **↑**
  - being trained on → utility **↓**
- Stale selector → **priority inversion**: re-picks already-harvested clients, ignores clients quietly accruing high-value data
- **Heterogeneity multiplier:** at α=0.1, *which* client you pick matters most → worst-case regime, by design

### Felix's fix
- **Eval-driven utility refresh** → priority tracks the moving target instead of lagging it

### The oracle (how we prove it w/o ground truth)
- Per baseline `B`, run paired **`B_oracle`**: same selector, true current utility injected each round
- = that baseline's **performance ceiling** (zero misprioritization)
- **`B` vs `B_oracle`** is the clean measurement

### Claims → what we capture
| Claim | Data |
| --- | --- |
| **1.** streaming makes utility dynamic; systems don't model it (utility ↑ with data, ↓ after participation; rising-but-unpicked client) | `oracle_utility.csv` — true per-client trajectories + top-K churn heatmap |
| **2.** stale prioritization → slower time-to-accuracy | `oracle_misselection.csv` — mis-selection rate, utility regret, correlated w/ time-to-60% |
| **3.** Felix does its job — smallest **staleness tax** `T(felix) − T(felix_oracle)`, closest to true top-K | paired time-to-target + overlap-with-oracle |

- **Headline number:** per-baseline **staleness tax** (time lost purely to stale prioritization)
- Thesis: Felix's tax is smallest, and the gap **grows** under staggered streaming (phase 2)

# Part B — Simulation harness (high ROI)

### Why
- Each study = 4 baselines × paired oracles × conditions
- Real hardware (300 clients, MQTT): **tens of hours / config** → ablations infeasible
- Simulator runs the **same** code on a **virtual clock** → **few hours**, deterministic
- Leverage **across every project** on this stack

### The hard part: fidelity, not speed
- **Parity ladder:** `clock → availability → selection → training → aggregation → utility → outcomes`
- Auto-localizes the **lowest broken rung** (downstream breaks are consequences, not bugs)
- Issues found + fixed: aggregation-correctness regression, per-commit overhead model, eval/checkpoint off critical path

### Fidelity + speedup scorecard
*45-min · n=300 · 100% avail · sim reproduces real behavior; all gaps within tolerance*

| Baseline | speedup | rounds real→sim | advance real/sim | staleness real/sim | acc diff |
| --- | --- | --- | --- | --- | --- |
| feddance | **18.4×** | 365→370 (+1.4%) | 33.85/34.11s | 183/185 ✓ | 0.029 ✓ |
| oort | **12.0×** | 666→701 (+5.3%) | 18.49/17.98s | 0/0 ✓ | 0.033 ✓ |
| refl | **2.31×** | 2016→1887 (−6.4%) | 1.48/1.74s | 3.02/3.00 ✓ | 0.034 ✓ |
| felix | **3.59×** | 664→667 (+0.5%) | 4.52/4.95s | 2.79/**7.19** ✗ | 0.024 ✓ |

- Rounds + advance + accuracy match → sim reproduces **what** the system does, not just speed
- One open item: felix **staleness** (root-caused — clock/commit-ordering under contention, *not* a selector bug; doesn't hurt accuracy parity)
- **ROI:** tens of hours → few hours, deterministic, same production code
